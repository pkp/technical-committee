### 1. Validation and feedback for proposed changes for 3.5 to Masthead/ORCID/GDPR

#### Masthead

https://github.com/pkp/pkp-lib/issues/13370

Alec: Adjustments were made on the masthead settings (allowing users to enable/disable). Mostly solves the problem.

#### GDPR

Users invitations: It's no longer possible to just assign roles.

- Ronald
    - We're using available work-arounds with success:
        - "Log in as" provides an option
        - Admin interface provides an option
    - Email delivery is sometimes an issue. Mainly when email addresses have changed and the user hasn't updated their account.
    - Maybe "Log in as" could become more GDPR compliant by making it optional to the role, e.g. "this role is allowed to log in as"
- Martin
    - Also problems with accounts that have out of date emails
- Carolina
    - "Log in as" not always a useful option because of multijournal environment.
    - You need to be an installation admin if you want to assign roles without invitations.
    - Not sure yet whether email-based invites is a big issue or not since journal managers can't edit profiles for users with roles in multiple journals anyway.
- Marc
    - "Log in as" is still very useful. Please don't remove it (yet), even though it's hard to square with GDPR requirements. May be we can make it explicit registering in article's log when an action was done under "login as"?. Ideally: Also mail the user about the changes made in their behalf.
        - Sebastian: We have a "deputy-feature" in our public infrastructure tools where "login as" can be enabled for a specific user by the user that can be logged into as well. I doubt that they haven't checked this for compliance
        - Martin: (we use it mostly for the same reasons as Sebastian mentioned -verify/reproduce actions for supporting users)
        - Marc: Alec, do you think this is feasible? "Can make it explicit registering in article's log when an action was done under impersonation?"
            - Alec: Yes, it's available in 3.6.
    - GDPR is not a "firm" technical requirement. Management decisions are also up to the manager to make. If journals are clear in the "Privacy Notes" about how they deal with data, registering users could still be a legal practice.
    - Email delivery is a problem we all have; getting bigger. In the past, emails were solid, but email handling monopoly by big companies is making it less so. Managing mail bounces is a very time consuming for administrators and we need to thing about how to make it easier.
- Antti-Jussi
    - The invite option was important especially for multijournal installations and originally the invite option was suggested as a solution for this. A situation where user is in Journal A but not in Journal B and the editor in Journal B can not add roles for the user and manage the user. I do think that we could still allow creating user accounts to their own journal if the user does not exist [Carolina: at least for 3.4 it's possible, they can also add roles for users that only have roles in that specific journal]. This could be higlighted as something that might not comply with GDPR but would be the journals decision.
    - Reviewer workflow, not yet finished, is still important. Either continue the work started by TIB, or allow for a reviewer to remove their acount on rejection if they want.
    - Journals should have tools for their own management, so we don't have to deal with it via support tickets as site administrators.
        - Carolina: I very much second that
    - We should be more careful about introducing big changes.
        - Marc: We should introduce these changes little by little and see how users react--they should also be able to choose to use/activate these features*.
- Alec
    - How much of this is tied to global user model? Is it worth considering a bigger change?

Summary: Not everyone uses 3.5 yet, but issues here were less urgen than expected. Email delivery is sometimes a problem but not universal or existential; "log in as" and admin work-arounds are OK for many installs, but bigger/more mixed installs (like SciELO's) run into admin roadblocks. 

#### ORCID

Alec: Mainly technical changes. ORCIDs are required for authors before publication, which implies they need to authenticate their ORCIDs as adding them manually is no longer an option. (ORCID authentication specifically?)

Improvements are coming here: https://github.com/pkp/pkp-lib/issues/13283

- Emily Q: How much are you seeing ORCiD used? For us, it's a nice-to-have that we see sometimes.
    - Ronald: It's frequently used. Editors often want it. Authors often use it.
    - Marc: ORCiD is important, but with focus on digital sovereignty, centralized service is a risk. We need author IDs, but need balance against risks.
- Martin: We impose OIDC, ORCID on our UZH platform. We are required to do so because of 2factor authentications.
- Carolina:
    - We don't publish on OJS, but we require ORCiDs in our XML. Authors are asked to add them into their manuscript.
- Q: Are there plans for 2FA built into OJS?
    - Alec: We're hoping to integrate support (previously external in OpenID plugin) into core with 3.7 (not confirmed yet). Will use Laravel Socialite. Reduces our tech debt, integrates better/more flexible support.
- Sebastian:
    - We sometimes have problems with authors who just can't/don't verify their ORCiDs. Not sure details, but we work around via cumbersome debugging in code and admin work-around. Seems completely random, possibly an ORCiD API failure?
    - Alec: When 3.5.0-6 comes out, please try that; then please debug with us on Mattermost
